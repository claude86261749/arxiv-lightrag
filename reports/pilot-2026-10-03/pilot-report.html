Paper graph pilot: 20 papers, cs.IR

The nine-stage pipeline from the design draft ran end to end on 20 recent cs.IR papers. The first run exposed four bugs in entity resolution. After fixing them, a second run passed every automatic gate. Merge precision was 117 or more out of 121 on my review; a person still has to check it.

3 October 2026. LightRAG 1.5.7, gemini-3.8-flash, gemini-embedding-2 at 768 dimensions. Code and outputs are on branch claude/epic-goodall-dglc5e of claude86261749/arxiv-lightrag, with outputs under reports/pilot-2026-10-03/.

Where it stands

Ready for the 200-paper phase once three things are settled. A person needs to check the merge review sheet. You need to confirm the corpus source, since the pilot converted arXiv's HTML pages itself. And the design calls for Postgres storage from 200 papers, which isn't built yet.

Cost and time: $0.24 and 46 seconds per paper at the pilot's settings. For 1,000 papers that is about $240 at prices valid to 31 December 2026 (about $480 after) and about 13 hours with no parallelism changes.

What ran

  • Corpus. The 20 newest cs.IR papers (primary category) that have an arXiv HTML version, submitted late September to early October 2026: 2.9K to 17.5K words each, mostly recommendation, generative retrieval and RAG. The Markdown comes from a converter written for the pilot (kgpipe/fetch.py). It keeps heading levels, in-text citations as links and one line per reference entry.
  • Run 1. All nine stages, gleaning on, appendices cut. It found the problems listed under entity resolution.
  • Run 2. The same 20 papers from scratch, after the fixes. Every figure on this page is from run 2 unless it says otherwise.
  • Appendix comparison. The 7 papers with large appendices, ingested again with appendices kept.

Thinking tokens are about half of all output and are billed as output. LightRAG's own token counter leaves them out; the pipeline now records them separately. Setting a lower thinking level for extraction is the largest cost lever not yet tested.

Wall time was 15 minutes: 6 for ingestion, 7 for resolution, 2.5 for graph cleanup. Throughput was capped by concurrency settings (8 LLM calls at once), not by rate limits; nothing was throttled. Resolution applies merges one at a time, and each merge re-embeds the node's relations, which accounts for most of its time.

The pilot's three measured choices

Gleaning: keep it on

The gleaning pass added 501 new entity names to the 2,270 from the first pass (22%), and 47% more relation rows. That is above the draft's 10% bar. A sample of the added names is mostly useful (TREC, Cross-Encoder, Latency, Named Entity Recognition), not noise. It costs a third of ingestion spend.

Appendices: keep cutting them

On the 7 papers with large appendices, keeping them added 95 chunks (+86%) and 430 entity names (+66%). The added names are mostly setup detail: optimizers, GPUs, hyperparameters and table header tokens such as #tok and Acc.. Across all 20 papers, appendices are 82K tokens on top of the 172K kept, so including them would add about 48% to extraction cost.

Neighbour threshold: 0.90, or 0.85 with lexical support

At the draft's 0.85, only 4–8% of vector-only pairs between 0.84 and 0.90 were duplicates, against 14–22% above 0.90. The loose pairs also chained into connected groups of 78 and 95 names. Splitting those into clusters of 8 silently dropped pairs, including LLM / Large Language Model.

The new rule keeps a vector pair only at 0.90 or above. A pair between 0.85 and 0.90 is kept only when the names share a word or one looks like the other's acronym. On run 1's decisions, it keeps 82 of the 86 confirmed duplicates with 47% fewer pairs. Lexical pairs may now cross types, because the same name gets different types in different chunks.

Corrections to the design draft

  • LightRAG runs in-process. Ingestion uses the same enqueue path as /documents/upload, so parsing and chunking are identical. The server has no route that returns entity vectors, and merging joins descriptions without summarising them. Both stages 6 and 7 need the Python API. The server can still serve the same storage afterwards.
  • LightRAG's Gemini embedding binding fails with gemini-embedding-2. A batch of texts comes back as one vector, so every vector-store write fails. The pipeline calls batchEmbedContents directly.
  • The paragraph chunker's size setting is CHUNK_P_SIZE, default 2,000. It does not inherit the 1,200 default; the pipeline sets it.
  • Type guidance can't be set through an environment variable on the server. It needs a YAML prompt file that also contains extraction examples. In-process it is a plain addon_params value.
  • MAX_GLEANING above 1 has no effect. LightRAG runs at most one gleaning pass.
  • Open question answered: the per-document entity lists keep extracted names after merges. 152 rows still hold alias names. The paper-to-concept export maps them through the alias table, as the draft planned.
  • Cleanup rules. With arXiv HTML as the source, the running-header and hyphenation rules have nothing to do. The repeated-line rule had to be tightened, because table cells repeat too. The "removed over 50%" flag now leaves appendices out, since long appendices tripped it on 4 of 20 papers.

Before the full run

  • Review two sheets. Mark review_merges.csv (121 rows) and the stoplist against the hub list. This is the one gate I can't close.
  • Confirm the corpus. Which category, and where the Markdown comes from. If it comes from a PDF converter, the cleanup rules need a 20-file check on that output, as the draft says.
  • Build Postgres storage for the 200-paper phase. The draft moves vectors and key-value stores to Postgres with pgvector at 200 papers. It isn't built; the pilot used LightRAG's file storage.
  • Raise parallelism. At 8 concurrent calls, 1,000 papers take about 13 hours. LightRAG's concurrency can go higher within the rate limits, and resolution could batch its merges.
  • Optional: test a lower thinking level for extraction. Thinking is half the output cost.

Run the pipeline with python -m kgpipe.pipeline --corpus <dir> --run <dir>. Each run writes report.json, quality.json, review sheets and exports.
